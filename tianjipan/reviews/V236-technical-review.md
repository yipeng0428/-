# 天机盘 V236 技术审查

本次结论：V236 已具备较丰富的可运行功能，但存在已复现的导入脚本注入、保存失败被当成成功、跨人物校准污染和计算模块接口错误。建议在继续扩展 V237 历史锚点前，先修复这些影响数据安全与结果可靠性的路径。性能优化空间也很明确，主要来自历史补丁的重复初始化、重复加载、样式和 DOM 工作，而不只是数学计算速度。

这是代码和浏览器运行审查，未修改上传的 HTML，未验证所有术数规则或古籍解释的正确性。完整量化证据见同目录 `V236-review-evidence.json`。

## 1. 人物导入的持久化脚本注入

定位：主脚本的 `pplImport()`、`pplRepairData()`、`pplBook()`，以及后续首页人物卡/人物册模板。主文件约 9753、10056 行，后续人物模块也存在直接插入 ID 的模板。

导入路径把 `raw.id` 转成字符串并保留，修复函数也只处理空 ID 与重复 ID，没有限制字符集。显示姓名时使用了 `esc()`，但显示 ID 的 HTML 属性没有同样转义，例如 `data-id="${p.id}"`；其他模板还将 ID 放进 `data-home-person`、`data-home-del` 或文本。

通过真正的 `#prbImp` 文件上传入口导入含恶意 ID 的 JSON，可以结束属性并插入带事件处理器的标签。测试只执行了 `window.__importAudit = 1`；导入后执行成功，刷新页面从 localStorage 恢复数据后再次执行。说明这是持久化导入问题，不是只在开发者控制台手动执行脚本。

适用条件：需要用户导入恶意人物 JSON。没有证据表明任意远程访客可无需交互直接触发。当前账号后端未配置，但页面本来就会保存人物资料，且可选保存 AI Key；若未来启用云会话，本地 Token 也位于同源存储中，影响会扩大。

建议：

1. 导入数据时生成新的内部 ID，并用 Map 映射旧 ID 与关系外键。若确需保留旧 ID，严格限制为约定的标识符格式，不让外部 ID 作为 HTML 片段使用。
2. 使用 DOM API：`element.dataset.id = id`、`textContent = name`。仍用 HTML 模板的地方必须做属性上下文转义。
3. 遍历所有人物/关系/外部导入模板，不能只修一个首页按钮。移除 DOM 里的危险内容后，持久层也要迁移；仅删除内存对象不能解决刷新恢复。
4. 富文本使用经过维护的 sanitizer，并配合严格 CSP。现有 `sanitizeHTML()` 有积极作用，但目前没有覆盖人物 ID 这条入口。
5. 增加文件导入、显示、刷新恢复的回归测试，断言危险属性和事件处理器不存在。

## 2. 保存失败与界面成功提示冲突

定位：`pplSave()`、`prbCommit()`、`TJPeople.add()/update()`、人物册保存按钮；主脚本约 9595 行，人物公共 API 约 16914 行。

`pplSave()` 遇到存储异常会返回 false，但上层忽略返回值，继续更新内存并提示“已新增”或“已保存”。测试让人物存储键的 setItem 抛出 QuotaExceededError，结果是：内存有 1 个人物；存储没有改变；最后 toast 为“已新增”；刷新后人物数量为 0。

还有部分提交的风险：主键先写入，兼容 v3 镜像随后写入；第二次写入失败时，函数把整个操作描述成失败，即使主存储已经更新。镜像与主库不是原子事务。

建议先建立持久化提交的返回契约，如 `{ok, persisted, reason}`，持久化成功后才显示“已保存”。保留未保存编辑以便重试，不静默丢弃。主库与镜像应分开报告，逐步移除重复写入；多人关系等结构数据适合 IndexedDB 事务。设置容量限制、导出备份和恢复入口，并测试完全拒绝写入、主键成功镜像失败、存储损坏三种情况。

## 3. 量天尺结果与人物校准没有统一

定位：`v235-liangtianchi-js` 的 CAL_KEY、CAL、saveCal、limitAtSui、augment；`v236-liangtianchi-grid-js` 的 augment、currentMapping、q236Apply。

复现：人物甲 1990-01-15 12:00，宫内度约 24.7395°，V236 自动年龄为 19；将此年龄写入 V235 校准。再切换人物乙 2000-06-10 07:00，其宫内度约 19.3848°，V236 自动年龄为 17，但 V235 仍持有甲的 19 岁校准和备注，并据此生成乙的宫限。

原因：`tianjipan.qizheng.tonglimit.v235` 是站点共享的一个对象，没有人物 ID、出生输入或计算口径指纹。日期、地点、真太阳时及算法变化后也没有可靠失效机制。

另外，未手工校准时，V236 可以显示自动结果，但 V235 的 segment 仍为 null；`autoAppliedToV235:false` 明确表明两条计算路径没有合并。因此“自动童限映射已生成”不等于“下游所有宫限已经使用新结果”。不自动持久化是合理选择，不必因此强制落盘，但计算链要明确选择同一个有效结果。

建议把手工 override 与自动值分开，用 `profileId + inputFingerprint + ruleVersion` 标识校准。统一 effectiveStartAge：有效的人物手工校准优先，否则用当前自动值；下游仅从这一入口读取。切换人物、改变出生信息、切换口径都应重新验证 override。旧全局校准无法安全归属时，不应自动应用到所有人物。

## 4. 紫微飞星增强层存在作用域错误

定位：`v112-qimen-ziwei-js` 内部的 `zBirth()`；`v203`、`v204-ziwei-chain-timing-js` 的 layerSet/build/scan。V204 首次调用约 35655 行。

`zBirth()` 定义在 V112 的 IIFE 内部，没有导出。V203/V204 位于其他 IIFE，却直接调用该函数。V204 selfTest 返回 `zBirth is not defined`；打开紫微飞星页面可见“运限时序叠层”错误和“四化转链层渲染失败”。基础飞星图仍能显示，不能因此认为整个增强层工作正常。

建议导出一个正式的出生输入转换 API，或者在独立模块中共用同一个函数。不要继续通过 window 临时加别名来掩盖所有依赖边界。测试应覆盖有当前命盘的分析、时序叠层与扫描；无命盘时应记录 skipped，不能把跳过当成算法通过。

## 5. registerRule 缺失导致后续注册中断

定位：`v85-tianji-core-js` 的冻结公共 API；V223/V226/V228/V232/V233/V234/V235/V236 的 registry 段。

核心只有 registerEngine、registerSource、registerLicense 等接口，没有 registerRule。浏览器确认这 8 个模块启动时发出 TypeError 警告。它们用同一个 try 包裹 source → rule → engine 的注册，因 rule 调用失败，后续 registerEngine 不再执行。例如 V236 的 `qizheng.liangtianchi.grid.v2` 没有进入核心引擎列表。

模块自身的窗口 API 仍存在，因此界面部分功能能运行，但统一引擎调用、来源登记和能力清单已经不一致。

建议先明确规则注册契约：实现规则目录、版本和来源检查，或删除并迁移无效调用到真正的规则系统。启动时检测接口兼容性，并对关键注册失败给出可见状态。单元自测要断言模块进入 registry，而非仅断言 wrapper 曾经安装过。

## 6. 同一个计算输入受当前表单状态影响

定位：主 `qzCalc(R)` 的 `readOpts()` / `nwSun()`，约 7140 行；V233 用 q.isDay 推导昼生/夜生的强弱信息。

固定一个出生地点为 117.8°E 的输入对象，仅改变当前表单经度：117.8 时 isDay=true；-120 时 isDay=false，V233 昼夜分类也跟着变化。输入对象的地点仍为 117.8，调用的仍是同一个 qzCalc(input)。

这会影响人物派生、多人比较、报告与批量计算，不能用缓存简单掩盖。V235 hintFromDegree 也会在计算传入人物时访问当前全局 R，存在类似上下文混用。

建议把地点、时间、流派、历元、provider、校准作为显式 context 参数。计算函数不读取 DOM 或当前选中人物；UI 适配层负责构建 context。增加不变性测试：相同 input/context，在改变当前表单、切换人物前后输出应相同。缓存键也必须包含这些真实依赖。

## 7. 现有 QA 无法可靠判断发布状态

运行 full QA 返回 51 项：38 pass、6 warn、6 fail、1 info。这里有真实功能失败，也有 QA 自身的过期假设，不能简单表述为“网站 6 个功能坏了”。

- 版本检查仍要求 title 和 buildVersion 同时包含 V215；真实标题是动态时辰，版本号还会被旧脚本写成 V219、v137 或懒加载后 v173。
- TianjiConsumerReport 实际导出 build、last、toText，QA 却要求 report、textReport。
- TianjiLiuyaoDepth 没有 selfTest，QA 却将其列为必需接口；这说明契约和测试维护没有跟进。
- fullRegression 先 quickChecks 再加载懒模块，因此把 TianjiEvidence 尚未加载记录成失败后，没有复查。
- V228 的锚点已修为 Julian 1578-01-08 / proleptic Gregorian 1578-01-18，但自测仍要求 Gregorian 是 1 月 8 日。这是过期断言，不是据此证明历元转换有误。
- STATIC.syntax_errors=0 等是写死的构建基线，不能验证后来增加的脚本。本次 184 段语法通过来自实际外部检查。
- 多个 selfTest 返回启动时缓存的 TEST，不能发现之后的状态变化。
- factory smoke 只看是否返回非空字符串，模板已 catch 后返回错误文案时仍可被判作通过。
- 移动布局扫描没有识别可滚动祖先，把横向滚动容器里的表单/表格子元素当成溢出。实测页面宽度为 390；人物行宽 348，但 scrollWidth 为 1231 且 overflow-x:auto。应评价能否滚动访问，而非只看子元素 rect.right。

建议使用一个构建版本来源；测试基于 API 契约而非过期方法名。先加载必需模块，再检测接口，或区分 deferred/skipped/missing。动态失败不能被静态 pass 覆盖。发布检查至少包含人物保存恢复、导入安全、多人校准隔离、紫微增强、引擎注册、当前报告和手机操作，并直接检查预期输出。

## 8. 性能结果与优先优化方向

在本地 HTTP、空浏览器存储、拦截外部依赖的条件下，三次普通 CPU 冷启动：

| 测量项 | 本次观察 |
|---|---|
| DOMContentLoaded | 4.99 / 5.17 / 5.96 秒 |
| 首次内容绘制 FCP | 0.22 / 0.43 / 0.66 秒 |
| 超过 50ms 的长任务 | 24–30 个 |
| 最长任务 | 453–653ms |
| 这些长任务合计 | 约 3.28–3.52 秒 |
| 首屏外部请求 | 53 次，其中 iztro 48 次 |
| 4 倍 CPU 降速 | DCL 约 19.35 秒，最长任务 1.12 秒 |

早先其他浏览器运行 DCL 约 3.60–4.34 秒。云机器负载、浏览器插桩和并发检查会影响数字；这些不是线上实测、真实手机成绩、LCP 或 INP。部分普通 CPU 运行与另一浏览器审查重叠，因此不应据此承诺具体加速倍数。但“很早画出内容，之后仍有大量主线程工作”和“离线请求重复”都有明确证据。

### 优先 A：统一依赖加载

V91 的 loadVendor 没有 in-flight Promise 去重，V92–V106 等旧验证模块启动时反复调用它。离线失败时 16 条调用链分别遍历 3 个 URL，总计 48 次 iztro 请求。应建立每个库唯一的加载 Promise、状态和失败冷却，用户显式重试再刷新状态。校验台依赖优先在进入校验页面时加载，不必占据首页。

检查 npm 1.7.7 包并验证 tarball 完整性后，还确认 lunar-javascript 的 npm 包有 `lunar.js`，没有 `lunar.min.js`。当前 jsDelivr npm 回退地址指向后者，需改为实际存在的资源并核验。不能通过改地址或关闭校验来“假通过”。

### 优先 B：停止把历史版本全部当成启动代码

184 个 script 块多数立即执行，只有 6 个 Insight 脚本被标记为延迟执行。它们仍内嵌于文件中，所以当前机制减少 JS 执行时机负担，却不减少 HTML 下载量。主脚本本身约 2.25 MB；大量后续样式反复叠加。

先提取当前有效实现和必要兼容适配，不直接删掉全部旧版本。通过固定样本对比新旧输出，再逐个删除多余 wrapper、版本修改器、重复声明和样式。开发源码模块化后，仍可在发布时打包成一个 HTML，离线分发与可维护性可以同时保留。

### 优先 C：把 DOM、样式和数据计算分开

首屏约 4,000 DOM 元素，进入七政页面约 7,100。多个版本以定时器分别 mount 自己的面板；每次 mount 又替换整段 HTML 并重算当前结果。应在一次 render 流程中生成当前计算快照，所有面板共享同一份快照；静态古籍、矩阵和元信息不要在每次输入变化时重建。

根据需求折叠历史证据板，打开后才构建其 DOM。此举比把卡片 display:none 更能减少首次构建成本。大结果列表可分页或虚拟化，先测实际规模再决定。

### 优先 D：真正接入生命周期

源码已有 Scope、register/mount/unmount，这些是好的基础；但运行快照只有两个模块处于 registered，没有 mounted。旧模块仍直接维护自己的监听器、观察器和 timer。首轮记录到 25 个 MutationObserver 实例和多次高频回调；这不等于已证明内存泄漏，但说明新机制没有覆盖主要运行路径。

将每个页面的监听、计时器、RAF、观察器统一交给 scope。页面切出时 unmount，重新进入时 mount；document.hidden 时暂停动画，减少动态效果时保留功能但停掉装饰动画。优先替换三个 80ms 轮询和全 body 观察器为局部事件或有界观察。

### 优先 E：最后再决定 Worker 与缓存

先修纯函数边界和缓存键。对同一时刻/地点/口径的天文结果建立有界 LRU；对择日区间、关系时间轴或批量历史扫描等实测超过主线程预算的任务使用 Worker。带 requestId，取消或丢弃过期结果，避免旧任务覆盖新人物。

并非所有计算都适合 Worker。大量时间消耗在样式和 DOM 上时，把函数搬进线程不会解决卡顿。SSE/网络解析通常也不必全放 Worker。需要 profile 来决定。

gzip 压缩估算约 1.90 MB（约原文件 32%）。站点部署可开启 gzip/Brotli，结合缓存策略降低传输；它不会降低解压后必须解析/执行的内容量，也不改善本地 file:// 的磁盘文件大小。图片不是本文件体积的主要证据方向。

## 9. 输入验证、完整性和安全边界

### 日历与度数

TianjiTime.createContext 接受 2023-02-29、2024-02-30、2024-04-31。当前 validateCivil 只检查 d<=31，未按月份和闰年检查。输入年份/月日应为整数，时分秒应有限，不能用 `x || 0` 把 NaN 当成合法零。校验应位于计算入口，不只依赖 datetime-local 控件，因为 JSON、API 和旧存档可绕过 UI。

V236 的 `Number(null)`、`Number('')`、`Number(false)` 都为 0；ageFromPalaceDegree 因此返回 11。输入未知值不能冒充合法 0°。应先拒绝 null、空字符串、布尔值，明确负数/30°/360°是否允许归一化。`+1e-10` 还让略小于 3° 的值进入下一格，应明确定义容差与展示误差，而非只在 floor 前添加魔数。

### 第三方代码

V227 星历源码执行前校验固定字节长度和 Git blob SHA-1，是已有的有效控制。旧 lunar 与 iztro 路径直接执行网络或 localStorage 的源码；声明过 gitBlob/packageIntegrity 并不意味着实际执行了验证。建议所有 vendor 统一由可信构建流程获取，锁版本与哈希，保留许可证，优先随构建打包；必须运行时加载的资源才走固定来源和执行前验证。

不建议把“eval 存在”本身当成任意执行漏洞：V227 有明确校验。但 eval 方式会妨碍严格 CSP，适合迁移为可信模块或构建时依赖。没有在本次证明 CDN 已被篡改。

### 凭据与后端

账号会话在 localStorage；AI Key 默认 sessionStorage，可选 localStorage。两者都可被同源脚本读取，sessionStorage 只是减少保存时间，并不隔离 XSS。正式联网版更适合后端代理 AI 调用、限制可访问上游、校验授权与配额；账号可按部署方式使用 HttpOnly/Secure/SameSite Cookie。保留用户自备 Key 的离线版时应明确储存范围，避免默认永久保存。

单独 HTML 不能保证云档案的服务端权限：需要检查 profile ID 越权、邮箱链接单次使用/过期、会话撤销、限流及输入约束。此次后端不存在于上传文件，不能下结论说这些已经安全或已经有漏洞。

## 推荐架构

不必为了重构先引入大型框架，也不必放弃单文件交付。可以采用“模块化源码 + 可复现构建 + 单文件离线产物 / 多文件在线产物”：

```text
src/
  core/          时间、天文、各术数的纯计算
  rules/         门派口径、古籍规则、版本与来源
  data/          地名、表格、固定金样、校准锚点
  storage/       人物 schema、迁移、事务、导入导出
  services/      账号、AI、可信 vendor 加载
  ui/            页面与交互，读取统一计算结果
  runtime/       生命周期、调度、错误与性能观测
tests/
  fixtures/      独立参考样本、边界、历史锚点
  unit/          纯函数与 schema
  browser/       保存恢复、导入、多人物、核心页面
dist/
  tianjipan.html 单文件离线发布产物
```

核心输入应包括出生 civil time、IANA zone/偏移决策、经纬度、真太阳时与换日口径、规则版本、历元/宿界、provider 版本、人物校准。输出带 input fingerprint、适用范围、来源与降级状态。不要在结果生成后再从当前 DOM 拼补这些字段。

历法/天文事实、流派规则、解释/评分三个层次应分别可测试。AI 消费结构化结果并解释，不改变已算好的事实。固定样本中使用独立预期值；拿自己生成的矩阵验证自己，不能证明古籍逐格转录或计算口径正确。

V236 的 12×30 表按同一个函数生成所有宫行，而源码同时说明逐格宿名字形尚未转录。因此“360 个单元格生成成功”“10 个区间覆盖成功”只证明结构与函数覆盖；如要声明逐格古表一致，应补来源页、格坐标、原字/校勘、换算口径和独立预期值。此审查没有据此判定三度映射本身错误。

历史时区依赖浏览器 Intl/tzdata；同年最小偏移推断 DST 属启发式。若需要跨机器长期复现，应记录解析出的 UTC、候选 fold 选择、数据版本/范围或保存完整解析证据，而非仅记录时区名称。

## 建议的版本顺序与验收

1. **V237 稳定修复批次**：导入 ID、保存失败、人物校准隔离、zBirth、registerRule、计算上下文、版本与 QA 契约。若 V237 已在做术数验证，可并行保留这些内容，但发布前应合入稳定修复。
2. **性能批次**：校验库单次加载，延迟校验台，去除旧版本 DOM 写入，统一七政计算快照，合并有效 CSS，接入真正的 mount/unmount。
3. **架构批次**：模块化源码、构建锁定、schema 迁移和可信依赖；把经过固定样本核对的现行逻辑逐个迁出。
4. **长期增强**：第二历史绝对锚点、长时段相位漂移、边界不确定性、独立 golden 对拍、在线版/离线版发布和恢复能力。

验收建议：

- 恶意人物 JSON 导入及刷新后不能出现事件处理器或脚本执行；非法数据给出明确错误。
- 存储失败不得显示已保存；成功保存后刷新能恢复；镜像失败与主库状态区分。
- 两个人物的校准独立；变更出生输入后 override 能明确失效或重新确认。
- 同一计算 input/context 不受当前表单与当前人物影响。
- 紫微增强页面、扫描与最新引擎注册实际通过，而不只看窗口对象存在。
- 正常/离线加载均只有一条共享依赖加载链；三来源回退最多按设计访问一次，不出现 16 条链。
- API/自测分别报告 pass、fail、skipped、deferred；门禁检测当前版本且无过期接口误报。
- 390px、430px、桌面关键操作可完成；横向表格能滚动访问；回归检查能识别滚动祖先。
- 用同一机器、同一配置重测三次，分别比较 FCP/LCP、交互延迟、长任务、脚本/样式时间、切页恢复和后台耗电。性能目标是工程预算，不提前承诺某个加速倍数。

建议把“当前显示结果来自什么时间、人物、规则、星历与校准”做成一个可展开的计算说明。这样用户遇到分歧时可以重现输入，开发者也能区分规则分歧、输入错误、降级和程序缺陷。
